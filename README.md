# Event Timeline Assistant

> ⚠️ **All data in this project is SIMULATED.** It was generated by a script and does not come from any real plant or equipment.

## 1. What it does

When an alarm goes off on a piece of manufacturing equipment, an engineer wants to know *"what else happened around that time?"*. This project is a small REST API (TypeScript + Express + SQLite) that answers that: it filters events, shows a ±N-minute timeline around a moment, and finds similar past events. An optional AI endpoint asks Google Gemini to summarize the timeline, and then plain code checks that every event ID the AI cites really exists, so made-up ("hallucinated") IDs get flagged.

The data: 200 simulated events over one week (2026-01-05 to 2026-01-11) for `Bioreactor-1`, `Pump-2` and `Sensor-DO-3`, of types `alarm`, `sensor_pause`, `work_order`, `batch_step`.

## 2. Tools and libraries, and why

| Tool | Why |
|---|---|
| **TypeScript** (strict mode) | Catches type mistakes before the code runs; the language the target roles use. |
| **Node.js 22** | Runs JavaScript/TypeScript on the server. Installed in a conda env. |
| **Express 5** | The most common, minimal Node web framework. v5 catches errors from `async` handlers. |
| **SQLite + better-sqlite3** | A real SQL database stored in one file, no server to install. Simple synchronous API. |
| **dotenv** | Loads `GEMINI_API_KEY` etc. from `.env` so secrets stay out of code. |
| **helmet** | Sets standard security headers (CSP, nosniff, frame blocking) and removes `X-Powered-By` in one line. |
| **express-rate-limit** | Caps `POST /ask` at 10 requests per minute per IP, so nobody can run up the Gemini bill. |
| **Gemini REST API** (via `fetch`) | Optional AI summary. Plain `fetch` instead of an SDK so you can see the actual HTTP call. |
| **Vitest + supertest** | Fast TypeScript test runner; supertest sends HTTP requests to the app without opening a port. |
| **tsx** | Runs `.ts` files directly during development (no compile step). |
| **Docker** | Packages the app and its exact dependencies into one image that runs anywhere. |
| **Terraform** | "Infrastructure as code": describes the AWS setup in files that can be reviewed and versioned. |

## 4. Setup

```bash
cd ~/projects/event-timeline-assistant
conda env create -f environment.yml      # creates the "event-timeline-assistant" env
conda activate event-timeline-assistant
npm install                              # installs packages into node_modules/
cp .env.example .env                     # then put your Gemini key in .env (optional)
npm run seed                             # builds events.db from data/events.json
```

No Gemini key? Delete the `GEMINI_API_KEY` line from `.env`. Everything works except the AI summary.

## 5. How to run it

```bash
npm run dev            # starts http://localhost:3000 and restarts when you edit code
```

Open http://localhost:3000 for the UI, or call the API directly:

```bash
curl "http://localhost:3000/events?equipment=Pump-2&type=alarm"
curl "http://localhost:3000/timeline?equipment=Pump-2&around=2026-01-07T10:30:00Z&minutes=60"
curl "http://localhost:3000/similar?eventId=EVT-0067"
curl -X POST http://localhost:3000/ask -H "Content-Type: application/json" \
  -d '{"question":"What happened?","equipment":"Pump-2","around":"2026-01-07T10:30:00Z"}'
curl "http://localhost:3000/timeline?equipment=Pump-9&around=soon"   # -> 400 with a clear error
```

| Endpoint | Returns |
|---|---|
| `GET /events?equipment=&type=` | Events, optionally filtered, sorted by time |
| `GET /timeline?equipment=&around=&minutes=60` | Events within ±minutes, plus counts per type (GROUP BY) |
| `GET /similar?eventId=` | Earlier events of the same type on the same equipment |
| `POST /ask {question, equipment, around, minutes?}` | Timeline + AI summary + citation check (summary is `null` without a key) |

**Tests and checks:**

```bash
npm test               # 22 Vitest tests
npm run typecheck      # TypeScript strict-mode check, no output = no errors
```

**Docker** (needs Docker Desktop):

```bash
docker build -t event-timeline-assistant .
docker run --rm -p 3000:3000 --env-file .env event-timeline-assistant
```

**Terraform** (only checks the files, creates nothing in AWS):

```bash
cd terraform && terraform init -backend=false && terraform validate
```

### How it's tested

- Each test builds a fresh **in-memory** SQLite database from 6 hand-written events, so results are exact and tests never touch `events.db`.
- `queries.test.ts`: filters; the window includes an event exactly 60 min away and excludes one 61 min away; GROUP BY counts; similar events.
- `api.test.ts`: every kind of bad input gets a **400** with a helpful message; unknown ID gets **404**.
- `citations.test.ts`: a fake AI that cites `EVT-0999` (not in the timeline) gets flagged. No network or API key needed, because the app accepts any function with the `Summarizer` type.

## 6. How it was built (in order)

1. Created the conda env (Node 22 + Terraform) and `package.json`; installed packages.
2. Wrote shared types (`types.ts`), then a seeded generator for 200 SIMULATED events.
3. Wrote the SQLite schema (`db.ts`), the seed script, and all SQL in `queries.ts`.
4. Wrote input validation that returns `Result<T>` values instead of throwing.
5. Wrote the citation checker and the Gemini client.
6. Wired everything into Express routes in `app.ts`; `server.ts` starts it.
7. Added the one-page UI.
8. Wrote Vitest tests (pure functions first, then HTTP with supertest).
9. Added the Dockerfile and the Terraform sketch; ran `terraform validate`.

## 7. Key concepts (interview-ready)

- **REST**: resources at URLs, HTTP verbs (GET reads, POST sends data), status codes (200 OK, 400 your input is wrong, 404 not found, 502 an upstream service failed).
- **Parameterized SQL**: `WHERE equipment = ?` with values passed separately. User input never becomes SQL code, which prevents SQL injection.
- **Indexes**: `(equipment, timestamp)` index makes "this equipment, this time range" fast.
- **ISO 8601 UTC timestamps as text**: same format everywhere means text order = time order, so `BETWEEN` works.
- **Validation at the boundary**: outside input is `unknown` until checked; errors say exactly what to fix.
- **Discriminated unions** (`Result<T>`): checking `ok` tells TypeScript which fields exist.
- **Dependency injection**: `createApp(db, { summarize })` receives its database and AI client, so tests can pass fakes.
- **RAG / grounding**: retrieve the relevant events first, give the model only those, require citations.
- **Don't trust the LLM**: code verifies every cited ID. The AI drafts, code checks.
- **Docker multi-stage builds**, **IAM least privilege**, **CloudWatch logs**, **secrets outside code** (`.env` locally, Secrets Manager on AWS).

## Limitations

- **The data is SIMULATED**: invented descriptions, regular 4-hour batch steps, and incidents that always follow the same pattern (sensor pause → alarm → work order).
- SQLite in a container is read-only demo storage. Real multi-user data would need a server database (e.g. Postgres on RDS).
- "Similar" means same type + same equipment, not similar text or root cause.
- No authentication, rate limiting, or pagination. The Terraform has no load balancer/HTTPS and was never applied.
- The citation check proves an ID *exists in the timeline*, not that the AI described that event correctly.

## How this would connect to real systems

- **Historian (e.g. AVEVA PI)**: alarms and sensor pauses would come from the historian's event frames / alarm history through its REST API (PI Web API). A scheduled job would pull new events and insert them into the `events` table (or the API would query the historian directly for a time window).
- **Work-order system (e.g. SAP PM, IBM Maximo)**: work orders would be pulled from its API and mapped to the same `PlantEvent` shape, joined by equipment ID (the systems often use different names for the same asset, so a mapping table is needed).
- **Batch/MES system**: batch steps would come from the batch execution system's records.
- Each source gets a small adapter that converts its data to `PlantEvent`; the API, SQL, UI and citation check stay the same.
